# Spotter

Spotter puts a player's card on screen the moment a high school announcer says their surname or cued jersey number, using Deepgram for the words and two saved rosters for the names. V3 rebuilds V2 as a new app with accounts, four roster formats and live football stats, and keeps V2's proven matching engine exactly as it was. This repo is V3 (`JedSandler/Spotter`, synced to `c607645` on Oct 8) moved onto the class stack: Railway Postgres with raw `pg`, Google and email/password sign-in, and its own Next.js server deployed by Railway. Live stats is part of it.

**The card** (Oct 3, made horizontal Oct 4; `docs/CARD_SPEC.md` is the full spec): one grey stage, the newest player's card a white strip 32em by 6.4em across it, and the two before as the same card at half size (`SMALL_SCALE`), side by side under it, so they say everything the newest does. Left to right: the number slab in the team's colour, with the position under it (the away team's slab always hatched and carrying its school code); the name, biggest text first (the respelling with its stressed syllable in heavy caps, or the surname), the name under it, and the player's storyline under that (two lines at most, Oct 7); and a stats column with a SEASON section and, on a game with live stats, a TONIGHT section on a grey band, always drawn. Each stat is its own row, written the way it is said ("420 yds", "5 TD"), and every stat shows (Jed, Oct 8: "No stats should get cut off!"): each group (passing, rushing, defense, ...) starts its own column, the biggest first, in spoken order, and the rows and text size are chosen per player so all of them fit the section's fixed box (`lib/cards/statLayout.ts`). Every size is em of one base size set on the stage from its own box, so a card never changes size, and nothing moves.

**The product spec is `docs/V3_DEFINITION.md`; the architecture is `docs/technical-design.md`.** Where the spec talks about Supabase or Vercel, the design doc wins. If neither answers a question, stop and ask Jed rather than deciding.

## Production Standard

This project follows the class Production Standard (the `production-standard` skill).

- Before finishing any change that touches auth, the database or migrations, API routes, rendering of user content, uploads, env vars, or deploy/CI config, run the `production-standard` skill and fix any Critical/High finding it reports.
- Known gaps and their status live in `docs/SECURITY-GAPS.md`. Update it when you fix or find one.
- **Identity comes from the session, never the request body.** Every query that takes an id from the request also filters by the signed-in owner, and a foreign id is a 404.
- **Sign-in is Google or email and password** (Oct 8). Google accounts are found by Google's `sub`, never by email alone; an email joins a Google identity to a password account only when Google has verified that email. Passwords are scrypt (`lib/server/password.ts`), emailed links are stored as SHA-256 only, and an email and password account must open its confirmation link before anything that spends money (`requireVerifiedUser()`). There is no approval step.

## Rules that do not bend

- **The hot path stays synchronous.** The function that handles Deepgram results and everything in `SpotterEngine.process` must not gain an `await`, a fetch or a storage call. Everything a live game needs is built before the mic turns on. Cards are direct DOM writes, not React renders: see `components/PlayerCard.tsx` and `components/NameDisplay.tsx`.
- **Do not change matcher scoring or thresholds** in `lib/matching/matcher.ts`. Import its functions, do not edit it. Numbers have their own knobs in the TUNING blocks of `lib/matching/numbers.ts` and `resolveJersey.ts`.
- **A bare number never fires.** A number reaches the screen only with a cue beside it: "number", a surname, or a team. Scores, clocks, downs and stats are vetoes in `numbers.ts`.
- **Keys stay server side.** `DEEPGRAM_API_KEY`, `OPENROUTER_API_KEY`, `RESEND_API_KEY` and the database URLs are read only in server code. Only `NEXT_PUBLIC_GOOGLE_CLIENT_ID` reaches the browser, with the build's own `NEXT_PUBLIC_DEPLOY_ENV` and `NEXT_PUBLIC_GIT_COMMIT`.
- **Never store an uploaded file.** No disk, no object storage, no logging of file contents or extracted text. Parse in memory and drop it. Errors and events carry codes and counts, never roster content.
- **The browser log never leaves the browser** except by the user's own Download, and, since Oct 5, a scrubbed copy (last names kept, first names and schools taken out) that goes to `shared_game_logs` at End game while the "Share game log" switch is on. That switch is on by default and the announcer can turn it off. Audio is never kept or sent. See "Sharing a scrubbed log" below.
- **Analytics never carry player names, jerseys, heard words, transcript or file contents.**
- **Schema changes are SQL files in `db/migrations/`**, applied by `scripts/migrate.mjs` on deploy. Never change a production schema by hand.
- **Secrets live in Railway's variables (one set per environment) and in `.env.local`.** Never commit a .env file, never ask anyone to paste a key into a session. `.env.example` holds the names and no values.
- **Verify before claiming.** A feature is not done because it typechecks. Run it, look at it, and say plainly what you did not verify.

## Auth and the database

- **Sign-in, Google:** the page asks `GET /api/auth/nonce` for a nonce (the raw value stays in an HttpOnly cookie, the page gets its SHA-256), hands it to Google Identity Services, and posts the ID token to `POST /api/auth/google`, which checks it with `lib/server/google.ts` and starts a session. An account is found by `sub` first; only a Google identity with no account yet uses its Google-verified email to find a password account to join (the rules are in the route).
- **Sign-in, email and password** (`components/auth/LoginForm.tsx`): `POST /api/auth/signup`, `/api/auth/signin`, `/api/auth/forgot-password`, `/api/auth/reset-password`, `/api/auth/verify-email` and `/api/auth/resend-verification`. Sign-up creates the account at once, signs it in and emails a confirmation link; sign-up, sign-in and the reset request answer the same whether or not the address has an account (AUTH-7). Passwords are 8 to 200 characters, not one of `lib/server/commonPasswords.ts`, hashed with scrypt in `lib/server/password.ts`. Emailed links (`lib/server/emailTokens.ts`, table `email_tokens`) carry 32 random bytes, store only their SHA-256 and work once. Email goes through Resend (`lib/server/email.ts`: `RESEND_API_KEY`, `EMAIL_FROM`, `APP_URL`), and nothing logs an address, a link or a token. A password reset signs the account out everywhere, then signs this browser back in. `/auth/verify` opens the confirmation link and `/reset-password` the reset link.
- **No approval step** (Jed, Oct 7: "get rid of all approval stuff"). Every new account, Google or email, is created with `users.approved = true` (`0013_no_approval.sql`). `approved` stays only as an off switch: as the database owner, `update users set approved = false where …` shuts that account out of everything that costs money (`usage_begin` answers `not_approved`, and the routes say `SWITCHED_OFF_NOTE` from `lib/usage/limits.ts`) and out of sharing a game log. There is no `/admin` page, waiting strip or disabled paid button.
- **Sessions** are `lib/server/session.ts`: a random token in `__Host-spotter_session`, only its SHA-256 in `sessions`. Never store or log a raw token.
- **Gates** are `lib/server/auth.ts`: `requireVerifiedUser()` before anything that calls OpenRouter or Deepgram (401 `signed_out`; 403 `not_approved` for a switched-off account; 403 `email_not_verified` for an email and password account that has not opened its link, which can still use everything that costs nothing; 503 `approval_unavailable` when the database cannot be asked), `requireUser()` for everything else signed in, `requireAdmin()` for admin (404 to everyone else), `getViewer()` for pages. `test/requireApprovedUser.test.ts` checks that each paid route refuses before any fetch; add a new paid route to it.
- **Limits.** The paid routes are limited by the spend guard (`beginUsage` right after the gate; see "Pre-launch fixes"), which replaced this repo's in-memory per-user limits on them. `lib/server/rateLimit.ts` (in memory, per replica, reset on deploy) still limits Google sign-in, password sign-in, sign-up, the reset request, the reset itself and the verification routes, by IP and, where the request names an address, by that address (429 `rate_limited`). Every state-changing route checks `isSameOrigin()`; `forUser` in `lib/server/route.ts` does it, and the sign-in check, for the data routes.
- **Queries** go through `lib/server/db.ts` with `$1` placeholders only, and an owner's data only through the owner-scoped repos in `lib/server/repo/` (`rosters.ts`, `games.ts`, `events.ts`, `account.ts`), which take the owner's id first and filter by it. The app connects as `app_rw_login` (rows only); migrations run as the owner. `lib/server/config.ts` refuses to start on Railway with any other database user or a public host.
- **The browser never talks to the database.** It calls same-origin `/api/...` routes through `api()` in `lib/apiClient.ts`, which never throws (a network failure is status 0). Where V3 calls Supabase from the browser (an insert, an RPC, a delete under row level security), this repo has a route and a repo function.
- **V3's names, our server.** Where V3 code imports a module that reads Supabase, this repo keeps the module's path, names and shapes and implements them on its own server, so V3's pages and components port unchanged: `lib/rosters/loadRosters.ts` (`loadTeamList`, `loadRosters`, `loadRosterState`, `loadRoster`, served from `repo/rosters.ts`), `lib/auth/viewer.ts` (`getViewerId`, `getViewerEmail`, `getUploadTermsAccepted`, from the session), `lib/server/usage.ts` (V3's `lib/usage/server.ts`: `beginUsage`, `finishUsage`, owner passed in), and `countsInSupabase()` in `lib/deployEnv.ts`, which keeps V3's name and means "this is production". **Keep to this:** when V3 adds a Supabase call, add to the shim rather than rewriting every caller, so the next sync stays a merge. The upload consent rides down from `app/layout.tsx` through `UploadTermsProvider` (`components/auth/UploadTerms.tsx`), as in V3.
- **Database functions take the owner first.** A V3 function that read `auth.uid()` takes `p_owner uuid` as its first argument here (`save_roster`, `set_season_stats`, `usage_begin`, `usage_finish`, `share_game_log`, `accept_upload_terms`, `record_client_error`, `delete_my_account`), and the route passes the session's user id. There is no row level security, no `auth.uid()` and no security definer to get past a policy: the repos scope by owner, and composite foreign keys refuse cross-owner rows.
- **A new table** goes in a new numbered file in `db/migrations/` (applied by `scripts/migrate.mjs` on every deploy; never change a production schema by hand), references `users (id) on delete cascade` through `owner_id`, and pins child rows to their parent's owner with a composite foreign key, like `roster_players`. Add what the app's role must be able to do to `scripts/check-app-role.mjs`. `app_rw` gets rows on every `public` table by default (see the traps).
- **Admin views and the off switch** are read and run as the database owner (Railway's database tab, or any SQL client with `MIGRATION_DATABASE_URL`), never through the app: the metric views, `admin.usage_by_user`, `admin.recent_client_errors` and `admin.pending_approvals` (always empty now), all in the `admin` schema, on which the app's role has no rights.
- **Daily cleanup** is `lib/server/housekeeping.ts`, started from `instrumentation.ts`: a minute after the server starts and then once a day it runs `delete_expired_shared_logs()` and `delete_old_client_errors()`, which V3 ran with pg_cron (Railway Postgres has none). Both are idempotent, so a restart or a second replica running them is harmless.
- **Local database:** `docker run -d --name spotter-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=spotter -p 55432:5432 postgres:18`, then `MIGRATION_DATABASE_URL=postgresql://postgres:postgres@localhost:55432/spotter APP_DB_PASSWORD=local npm run migrate`.

## Analytics

- `track()` in `lib/analytics/track.ts` queues in memory and sends batches to `POST /api/events` after paint. The vocabulary and the privacy filter live in `lib/analytics/events.ts`, which the browser and the route both run. **A string prop survives only if its value is declared in `ENUM_PROPS`.** A new event name needs `EVENT_NAMES` and a migration changing the `app_events` check constraint (in `db/migrations/`) together; a test compares them.
- **Only production counts** (Jed, Oct 7). `/api/events`, `/api/client-errors` and `/api/game-logs` record only when the server's own `RAILWAY_ENVIRONMENT_NAME` is `production` (the first two also drop anything from localhost), and `shareGameLog` sends nothing unless `countsInSupabase()` (`lib/deployEnv.ts`, from `NEXT_PUBLIC_DEPLOY_ENV`, which `next.config.ts` sets from `RAILWAY_ENVIRONMENT_NAME`). A local run still works and records none of it; rosters, games and the spend ledger are still written, because the app needs them to run.
- `app_events` takes at most 5,000 rows per account per UTC day (`app_events_daily_cap`, `0009_usage_limits.sql`).
- `account.signed_up` is sent when `POST /api/auth/google` says the sign-in created the account; a unique index keeps it to one per account. An email sign-up does not send it yet.

## Teams and roster import

- `/teams` lists saved teams; `/teams/new` and `/teams/[id]` are one screen, `components/rosters/RosterEditor.tsx`: team fields, import, the review table, Save, Delete. Save sends `PUT /api/rosters`, which calls `save_roster` with the session's user id; passing the team's id renames it in place, and without an id it matches by `roster_key`, so importing the same team again replaces its roster.
- **One reading path.** `POST /api/rosters/extract` runs `readUpload` (checks the multipart body) then `readRoster`, and every format ends in the same `extractRoster` call: a PDF's text layer as text (falling back to the PDF itself, which the model reads as page images), images as images, pasted text and spreadsheet rows as text. The prompt is `lib/rosters/extractionPrompt.ts`. Limits and failure codes are in `lib/rosters/extractErrors.ts`.
- The browser prepares files in `lib/rosters/importFiles.ts`: HEIC to JPEG with `heic-to`, oversized images shrunk to fit, CSV parsed (`lib/rosters/tableText.ts`) and .xlsx read with `read-excel-file` into " | " rows. Both libraries are loaded only when that kind of file is dropped.
- The review is `reviewRoster` in `lib/rosters/reviewPlayers.ts`. Common phrases heard during play are `lib/rosters/commonPhrases.ts` (meant to grow), scored through `scanWords` exactly like a live utterance. Look-alikes use V2's `findCrossPlayerCollisions` at the same "close" ratio as the common-word check, because Bargas and Vargas score just under the full threshold.
- **Storylines** (Jed, Oct 7): `roster_players.storyline` (`0012_save_roster_whole.sql`, from V3's `20261007203248`; at most 80 characters, `MAX_STORYLINE_CHARS` and `cleanStoryline` in `lib/cards/cardFace.ts`) is one line about the player, typed in the Storyline box of the team page's player table (`setStoryline`), kept by a re-import for the same surname and jersey, and shown under the name on the card (`face.storyline`, written by `writeCard`). Here `save_roster` writes it in the same transaction as the rest of the roster (an entry without the key keeps the same player's storyline), so V3's second write after the save (`rewriteAfterSave`) does not exist in this repo. It is roster content: never in analytics, and the scrubbed shared log carries no card faces.
- **Other info** (Jed, Oct 8, spec 6.6): the team page's third import (`components/rosters/StorylineImport.tsx`, an `ImportPanel` bar of kind `storylines`) takes any file or text and `POST /api/storylines/extract` (behind `requireVerifiedUser()` and `beginUsage`) has the model write one storyline per player it mentions, recent-game stats included (`lib/rosters/storylinePrompt.ts` is the tuning surface; `extractStorylines.ts` is the call). The page sends the table as `players` (`storylinePlayers`: row key, jersey, names, position, current storyline), so it works before the team is saved; the model answers by row key, `normalizeStorylines` keeps one per known player, never one the player already has, cut to fit by `fitStoryline`. `StorylineReview` shows each beside the current one, ticked and editable; `applyStorylines` writes the ticked ones into the table and Save keeps them. The spend guard counts it as `stats_import` (a new route name would mean a migration changing `usage_begin` and the `usage` table's check, and `USAGE_ROUTES` in `lib/usage/limits.ts`). Codes `bad_players` and `no_storylines`. `ImportPanel` also takes a `.txt` or `.md` file as text (`isPlainText`), for every import. Tests: `test/storylines.test.ts`.
- `lib/rosters/editor.ts` holds the editor's rules as pure functions: football offensive linemen (`isOffensiveLineman`) start with spotting off but are saved; a re-import keeps pronunciations and spotting settings for the same surname and jersey and drops season stats; `toSaveArgs` builds exactly what `PUT /api/rosters` sends and `save_roster` gets.

## Season stats and cards

- `/teams/[id]/stats` imports a team's season stats; `/teams/[id]/cards` previews every player's card. Both are linked from the team page, which asks first if the roster has unsaved edits: stats are matched to saved player ids, and a roster save replaces them.
- **Same four formats, one panel.** `components/rosters/ImportPanel.tsx` is the drop zone and paste box for both imports; `RosterImport` and `components/stats/StatsImport.tsx` wrap it. `POST /api/stats/extract` runs `requireVerifiedUser()` and `beginUsage` (`stats_import`), reuses `readUpload`, loads the roster with `getRosterForStats` (scoped to the owner), and calls `extractStats` (`lib/stats/extractStats.ts`). A stats PDF always goes as the document (page images), never its text layer.
- **Football is read in three calls at once**, one per group in `FOOTBALL_KEY_GROUPS` (offense, defense, special teams), each offered only its own keys, then joined by player (`mergeNumberReads`). One call writing every number on Brentwood's seven page MaxPreps sheet ran past the 120 s route budget. The prompt leaves zeros out and skips sections that only repeat numbers (All Purpose Yards, Total Yards, Scoring). Calls run at `effort: "low"`. The route logs one line per import with milliseconds and output tokens, counts only, so Railway's log shows how close a real sheet comes to the limit.
- **Football is numbers, every other sport is lines.** `statsKindFor` in `lib/stats/types.ts` decides. The prompts are `lib/stats/statsPrompt.ts`; football's schema is a list of `{ key, value }` pairs on the 9.2 keys, so nothing in it is nullable. The key list is `FOOTBALL_STAT_KEYS` in `lib/cards/statKeys.ts`; a test holds it equal to the spec and to `clean_season_stats` as the newest migration in `db/migrations/` defines it (`int_td` and `fr_td` came in with V3's `20260930214906`, here `0006_stats_keys_color_heard_as.sql`).
- Rows are placed by `matchStats` (jersey first, surname second, never a guess). A row that lands on nobody becomes a warning naming its jersey (`unmatchedWarnings`). The review's rules and exactly what `PUT /api/rosters/[id]/stats` sends (and `set_season_stats` gets) are pure functions in `lib/stats/review.ts`. A new import replaces the old stats, and `stats_as_of` defaults to today.
- **`lib/cards/` is shared card code** that the card path and live stats may both import, and that imports neither. `toCardPlayer` (`lib/cards/cardPlayer.ts`) is the one place that decides what a card says; the preview uses it, and the live screen's game builder must too. `seasonLine` (`lib/cards/lines.ts`) builds football's season line as items (`{ value, label, estimated, group }`): every group the player has, the biggest first, each in spoken order with every item (Oct 8: the old limits of two groups, five items and 10 characters are gone; the first item of each group names it, "64 car", "45 tkl"). **Nothing on the card is cut off** (Jed, Oct 8): `layoutStats` (`lib/cards/statLayout.ts`, pure, its TUNING block at the top) places every item of a section in a grid, each group from the top of its own column and on into the next if it is longer than the rows, and picks the row count and text size together so every column fits the section's width and every row its height (never past `MAX_STAT_SIZE_EM`; the most rows within `KEEP_ROWS_SHARE` of the biggest size wins, which keeps a group in one column). Widths come from the stage font's advance widths held in that file (measured in Chrome, the wider of weights 500 and 700, plus a margin), so no layout is read. `writeStatLines` (`components/PlayerCard.tsx`) writes the grid's size and each of the section's 40 slots' text, column and row, caching each line's layout in a WeakMap; each section is a fixed-height box (`sectionHeightEm`: SEASON the whole card without live stats, else `1 - TONIGHT_SHARE` of it). Another sport's saved lines (all of them, `face.seasonText` one a line) become items by `writtenItems`: a group a line, split where it lists things, long phrases broken into rows. Checked in Chrome with the stage font on Oct 8 at base sizes 16 to 56px: no row of any test player past its section. Tests: `test/statLayout.test.ts`, `test/playerCard.test.ts`. `lineText` turns a line into the text the card shows. `lib/cards/limits.ts` is for the text lines other sports import.
- **The card's strings are `face` on `WatchlistPlayer`** (`cardFace` in `lib/cards/cardFace.ts`, built by `toCardPlayer`): Title case for names saved in capitals, the first pronunciation note split once into `before`/`stressed`/`after` when it is a respelling (24 characters or fewer, letters, hyphens, spaces and apostrophes only), the small line, and the season line. `writeCard` (`components/PlayerCard.tsx`), for all three cards, only copies them into spans rendered once: text, hidden flags, the slab's three styles, and the number's and the big line's size. No as-of date, vitals, delta chip, key digits or borders on the card any more. A game built before `face` still loads and shows the saved names as they are.
- **The big line is fitted once per player, off the hot path:** `fitBigLine` (`lib/cards/bigLine.ts`, pure, widths from a measure function) breaks once at a hyphen or a space, then steps down from 1.8em to 1.55em and 1.3em, in a column of `TEXT_COLUMN_EM` (13.5em). `components/measureBigLine.ts` measures with canvas `measureText` once the stage font (`components/stageFont.ts`, Atkinson Hyperlegible Next through `next/font/google`, on the stage only) has loaded; `NameDisplay.prepare` runs it when a game opens and keeps the fits in a map `show()` reads. ## Live stats engine (spec section 8)

- **`lib/livestats/` is the engine.** `prompt.ts` is what the model is told and the schema it answers in; it is the tuning surface, and the fix for a wrong game is almost always a sentence there (the 8.5 phrasing guide lives in it). `openrouter.ts` is the call (Gemini 3.8 Flash, reasoning `minimal`, `OPENROUTER_TIMEOUT_MS`, instructions plus rosters cached), `extract.ts` builds the part that moves every call, and `validatePlays` trusts nothing in the answer. `POST /api/livestats/extract` runs `requireVerifiedUser()` and `beginUsage` (`livestats`), checks the body with `readRequest` (`request.ts`), and stores and logs nothing but a failure code. `cost.ts` turns tokens into dollars and into `game.ended`'s `tokens_*` props.
- **The rules are `apply.ts`, and only there.** The model says who did what; `applyPlay` turns it into numbers by R1 to R11 (spec 8.3), and every dropped event comes back with its rule. R11 (two-point tries add nothing), shared sacks (half each) and `int_td`/`fr_td` (R10) were settled with Jed after the spec was written; the spec says so now. `tonightTotals` (and on the live screen, `talliesOf` in `session.ts`) works tonight out from the whole list of applied plays every time, never a running count, so undo and a correction are both exact.
- **Unknown playerIds survive validation on purpose,** so R9 in `apply.ts` can drop them and the log can name the rule.
- **Every credit is checked before the rules see it** (`lib/livestats/check.ts`, run first by `readPlays` in `session.ts`). Since Oct 6 (after the two Gemini games, where the checks that second-guessed the reader fired 18 times and were wrong 17) **the reader decides what happened**: code applies a rule of football, fills in what has one answer, or drops what cannot be true, and **never moves a credit to another player**. The exceptions: an unnamed kicker on an extra point or field goal (R32, below), and a pass (or a sacked quarterback) with no usable passer, which goes to the quarterback on the field, estimated (R14; usable is on the roster, on the team with the ball, named in the words, and a quarterback or said to have thrown it, `saidToThrow` in `names.ts`). Position is used for that and nothing else (high school players go both ways). On a play from scrimmage (run, pass, sack) a carry or catch by the team without the ball is dropped, and a tackle, sack, breakup or forced fumble by the team with it, unless the ball changed hands or was returned (R12); kicks are not side-checked at all. Every credited player must be named in the read's transcript lines, first to last (R18; `isNamedIn` ignores case, hyphens, apostrophes, spaces and suffixes, and takes the whole surname split over up to three words or either half on its own; heard-as forms count). **Since Oct 10 (the Oct 9 high school game)** a close spelling names the player too (`namedIn` and `closeSpelling` in `lib/livestats/names.ts`: letters only, suffix off, doubled letters collapsed in both words, an edit distance of at most `closeLimit`, 1 for a surname of 4 to 6 letters and 2 for 7 or more, none for 3 or fewer, a possessive read as the surname, and only when no other player on either roster is as close to that word); the name check, and only it, also reads up to `LATE_NAME_LINES` (5) lines past the play's last line, stopping before the next play's first line and at the last line the reader has seen (`readThrough`); and a credit R18 dropped or R14 filled only because the player was not named yet rides on the play as `nameCheck` and is checked again on every reply (`readPlays`, a reply with no plays included) until those lines are in, when the reader's credit comes back with a `restored` note under the same rule. A play the announcer corrected is not checked again. Fills: a catch, breakup, interception or pass play with no passer is the current QB's (R16), a sack with no sacked QB too (R17), both estimated. R19 to R21 drop contradictions. Retired on Oct 6 and never reused: R13 (moves), R24 (touchdown removed by the score), R27 (a flag read afterwards wiped the play before it), R30 (a sack nobody called a sack was a run). `npm run replay:stats -- <log.json> --recorded` re-runs a log's recorded replies (`stats_reply`) through today's check and rules with no network (`recorded.ts`) and prints the totals the game counted beside today's, and every note with its rule.
- **One play, one record** (`lib/livestats/merge.ts`, run by `readPlays`; rewritten Oct 6). Each request lists the last five plays with their ids. A read is an applied play when its transcript lines are mostly that play's (shared lines over `SAME_LINES_SHARE`, half, of the shorter), else when the reader names it in `updates` (among the last `UPDATE_LOOKBACK`), else it is a new play: sharing one line or starting on the next line never makes two reads one play. `freshReads` lets such a read through below the watermark. The later read is checked on its own lines first (no fill-ins), then merged: a credit one player holds (passer, receiver, runner or sacked QB, kicker, punter, returner, interceptor, fumbler) goes to the update's player, or stays when it names nobody; tackles, sacks, breakups, forced fumbles and recoveries are added, each player once; the update's yards replace the old, except a worked-out figure over a stated one; a touchdown or a kick's result can be added by any update and taken away only by one whose lines cover the read that set it (`touchdownFrom`, `madeFrom` on the play); the play type follows the newest read (a flag or "other" read never changes it), and credits the new type cannot have go, so a play is a run or a sack, never both. The merged play keeps its id and status, so U takes it back once; it is logged as `stats_update`, which `foldStats` applies, and the strip says "updated". Totals are worked out from the play list, so an update never counts a play twice; a play the announcer corrected keeps the corrected numbers whatever a later read says.
- **Yards from where the ball is** (`lib/livestats/gameState.ts`, R23; Oct 6: only from a spot it can trust). The reader reports `startSpot` and `endSpot` (a yard line and whose half, `Territory`) and `shortBy`. The ball spot is fresh for a play only when the play states its own start spot, or the previous play's end spot is known and nothing came between (no penalty, no change of possession, no kick, no wiped-out play) and this play's stated down and distance match what the previous one implies (`missedPlayBefore`; a mismatch means a play was missed). A penalty moves the spot only when the new spot is said. Yards, first that applies: the number said; end spot (the goal line on a touchdown) minus a fresh start (`freshStart`); the change to the next play's down and distance on the same series with nothing between (`"downs"`); the stated shortfall; else blank. A spot said without a half sits in the known one's half only when that is under `NEAR_MIDFIELD`; a figure over `MAX_WORKED_OUT_YARDS` nobody said stays unknown. The previous play is back-filled when the next arrives, only with nothing between. A yardage said within `LATE_YARDS_UTTERANCES` lines of a play, before a down call, counts as stated; it replaces a stated figure only when the words look back at the play ("that went for 48").
- **The scoreboard** (`lib/livestats/scoreboard.ts`, applied by `readPlays`): the reader returns `score` whenever the booth states it. A touchdown is applied as read and confirmed when that side's score rises by 6, 7 or 8 at the next stated score; the score never takes one away (Oct 6). A confirmed touchdown whose side rose exactly 7 gets its extra point: a synthetic `extra_point` play (`xp-<playId>`) for the kicker already credited with a kick, else the roster's only kicker, else its only punter, when none was read, and `made` set on one read with no result (R25). A field goal with no result heard is good on a rise of 3 and missed on no change (R26). `touchdownChecks` says where each one stands.
- **Kick lengths** (Oct 5, `gameState.ts`): a punt's length is the line of scrimmage to where it came down (up to `MAX_PUNT_YARDS`, to the goal line on a touchback) and a field goal's is the yards to the goal line plus `FIELD_GOAL_EXTRA_YARDS` (17), both from a fresh start spot with R23 and `source: "spots"`. The prompt asks for start and end spots even when the yardage is said. A request is cheaper too: the transcript lines carry no seconds column, and a window is at most `MAX_WINDOW` (30) lines. The Oct 5 line to gain (`lineToGain`) is gone: it placed the ball across plays nobody caught, which is where the confident wrong numbers came from.
- **Penalties:** the reader returns `penalty` (`on`, `noPlay`, `beforeSnap`; a required object so it costs no nullable field). Only the reader wipes a play out: `nullified` or the penalty's `noPlay` on the play itself (the prompt says that includes accepted defensive pass interference on an incompletion), or an update that marks it so; a foul marked before the snap never wipes out any play (`wipedOut` in `lib/livestats/penalty.ts`, which R7 reads). A kickoff never adds a punt (R31, `apply.ts`). A punt with no punter named is that side's punter when exactly one player there is listed as a punter, estimated (R15, `fillPunter` in `check.ts`); none or several, and it stays blank. An extra point or field goal with no kicker read, or whose kicker the words never name, is the kicking side's kicker, estimated (R32, Oct 10, in `checkPlay`'s per-event loop like R14): `kickerFor` in `scoreboard.ts`, the one already credited with a kick tonight, else the roster's only kicker, else its only punter; nobody, and it is dropped as before. The prompt says a snap that is never kicked is not a punt. A run with an offensive foul during the play stands with its yards unknown and is not back-filled (R28).
- **Two misreads the words give away** (`fixMisreads` in `check.ts`): a `kick_return` on a play that is not a kickoff, or a pitch or handoff right after a missed field goal or a punt, is a run (R29). A sack is a sack whether or not the word was said. Upload consent is `users.accepted_upload_terms_at`, set only by `accept_upload_terms(p_owner)` through `POST /api/upload-terms`; ImportPanel asks once. Crash reports go to `client_errors` through `POST /api/client-errors` and `record_client_error()` (20 an hour per account, first line of the message, no query strings), read in `admin.recent_client_errors` and deleted after 90 days by the daily cleanup; `app/error.tsx`, `app/global-error.tsx` and `app/not-found.tsx` exist. `admin.pending_approvals` is always empty now that every sign-up is approved.
- **Shared logs** carry `owner_hash` (sha256 of the user id, worked out inside `share_game_log`), at most 5 a day per account, 6 million characters each.
- **Browser data** is stamped with the signed-in account (`lib/game/browserData.ts`, `ViewerStamp` in the root layout); another account on the same browser does not see it, sign-out clears it, and logs over 30 days old are pruned after paint, never on the live screen.
- **Live screen.** `IdleWatch` (`lib/game/idleWatch.ts`) stops the mic after 20 minutes with no words or 5 hours since Listen. `BrowserCheck` (`lib/game/browserSupport.ts`) says when this is not Chrome or Edge on a computer with a microphone. The token fetch gives up after 8 s (a G1 exception the spec now lists). User-facing copy says "speech recognition" and "name boost", never key names or providers.
- **Still owner actions:** spend caps on the Deepgram and OpenRouter keys; Resend's sender domain and `RESEND_API_KEY`, `EMAIL_FROM` and `APP_URL` in Railway's variables, without which no confirmation or reset email goes out. V3's other items (migrations to run by hand, Supabase Pro, custom SMTP, branch protection) have no counterpart: migrations apply on deploy and `main` is already protected.

## Traps this project has already fallen into

Each of these cost real time in V3. They are not hypothetical. (V3's Supabase, Vercel and iCloud traps are left out; the class stack does not have them.)

- **PDF.js detaches the array you open a PDF with.** `getDocumentProxy(bytes)` leaves `bytes.length` at 0, silently, so anything that needs the file afterwards sends an empty string to the model. Always use `openPdf` from `lib/pdf.ts`.
- **A nullable enum in a structured output schema needs `anyOf`.** `{ type: ["string","null"], enum: [...values, null] }` is rejected before the model reads anything, so it fails identically for every file. `test/extractionSchema.test.ts` guards this.
- **A stats table's meaning is in its columns.** Extracting text drops empty cells, so a ragged row cannot be aligned. Stats go to the model as the PDF itself, where the page image preserves the layout. Rosters are simple lists and read fine from the text layer.
- **`proxy.ts` makes Next buffer the request bodies it matches** and silently truncate them. Its matcher skips `/api/*`, so uploads never pass through it; keep it that way.
- **Tailwind's preflight honours the `hidden` attribute**, which is what lets the card slots be shown and hidden by DOM writes.
- **Deleting a route breaks `tsc` and `next build` until `.next/dev/types` is cleared.** A dev server that ran earlier left a validator that still imports the old route. With no dev server running, `rm -rf .next/dev/types` fixes it.
- **`numerals=true` rewrites more than numbers.** It is what turns "twenty three" into one `23` token, which is the whole reason jersey numbers work, but it also renders "half" as `0.5`, "quarter" as `0.25` and "third" as `3rd`. That shows in the transcript line and is harmless: a decimal is one of the shapes that can never be a jersey. Verified against the live socket and the pre-recorded endpoint, 2026-09-17.
- **Holding a number to the end of an interim costs a whole utterance.** An interim that ends on the number is the normal case when an announcer says a number and looks up, and Deepgram sends no further result until it decides the utterance ended. Holding every such number put the card seconds late; holding only the ones that could still grow into another jersey on tonight's rosters (`couldGrow` in `numbers.ts`) puts it up at about 1.2s, which is where surnames are. Measured against the live socket, 2026-09-17. Firing early is safe because a final that disagrees retracts it.
- **With `smart_format` off there are no punctuated tokens.** A score arrives as `"14","12"`, never `"14-12"`, and a clock as `"2","30"`, never `"2:30"`. Write fixtures from that, not from what a written transcript looks like.
- **The matcher joins short adjacent words, so a surname's span can swallow its own number.** "12 Chen" scores as one Chen candidate covering both words, because a number normalizes to nothing. Number tokens are excluded when surname spans are mapped in `parseJerseyMentions`, or a surname can never sit next to a number and nothing narrows.
- **A browser takes the wake lock back whenever the tab is hidden**, and does not hand it back when the tab is shown again. `useWakeLock` re-requests on every `visibilitychange`, and treats a release while the page is visible as a refusal, which is the only case worth telling the announcer about.
- **Tailwind only writes CSS for class names it can read in the source.** A size moved into a constant and interpolated into a className generates no rule at all, and the element silently falls back to whatever it inherits. That is why the card's em sizes are inline styles in `components/PlayerCard.tsx`.
- **A snapshot rewritten mid-game reaches the live screen through `useSyncExternalStore`**, and two things hang off that: the engine is rebuilt because `watchlist` is a new array (identity, not contents), and the socket reopens only when the keyterm list actually changed, because `useDeepgramStream` keys its effect on the joined keyterms. A refresh that changes no names does not reconnect.
- **`DeepgramStream` retries refusals it does not know are final.** Its fatal codes are `missing_key`, `invalid_key` and `forbidden`; `not_approved` (a switched-off account), `signed_out` and `email_not_verified` are not among them, so it keeps asking the token route with backoff. A new refusal code meant to stop the socket has to be added to its fatal codes, which is a G1 change.
- **`app_rw` has rows on every `public` table.** `scripts/migrate.mjs` grants select, insert, update and delete on all of them, execute on every function, and the same by default for anything created later. A table the app should reach only through a function (`usage`, `shared_game_logs`, `client_errors`) is still writable by the app's role directly, so owner scoping there rests on the app calling the function. Put a table the app must not touch in another schema, like `admin`.
- **Every guard in the upload routes has a code** in `lib/rosters/extractErrors.ts`. It reaches the browser, the terminal and `app_events` (as `prep.import_finished`'s `fail_code`, which lists every code). Add a code when you add a guard; a generic failure is what made the first roster bug take a whole session to find.
- **A markup test that looks for "disabled" matches Tailwind's `disabled:` classes.** Match the attribute, ` disabled=""`, or the test passes whether the button is disabled or not.
- **A database outage must not end a game.** The proxy only checks that a session cookie exists, and the live screen runs from what the browser already holds. The Deepgram token route does read the database (`requireVerifiedUser`, then `usage_begin`), and answers 503 `approval_unavailable` when the session cannot be read, which `DeepgramStream` retries with backoff; the spend check itself fails open for that route. `not_approved`, `email_not_verified` and `signed_out` are not in its fatal codes either, so the live screen has to refuse to start for an account that cannot get a token rather than rely on the socket giving up.
- **Catching every error in the session check hides Next's own signal.** Reading cookies is how a page tells Next it depends on the request; `lib/server/auth.ts` reads them outside its `try`, or the build tries to prerender `/games` and fails.
